# 측정 기반 결정 기록

기능을 넣기 전에 실제 도면으로 측정하고, 품질이 기준에 못 미치면 근거를 남기고
불채택한 기록입니다. 수치의 원출처는 [STATUS.md](STATUS.md) 작업 원장이며, 여기에는
외부에서 찾아보기 쉽도록 측정 방법·표본·날짜와 함께 정리했습니다.

## 가구 심볼 자동 인식 — 불채택 (2026-08-25 측정)

- 표본: Matterport 공개 샘플 BW Floor 1 (2897×2049px, 실측 1,214 sq ft).
- 방법: 이진화 후 중간 밝기 연결 성분을 추출해 가구 크기 범위의 후보를 세는 방식.
- 결과: 연결 성분 529개 중 가구 크기 후보 **3개** — 재현율 ~5% 수준. 원인은 가구
  심볼이 서로·벽과 맞닿아 하나의 거대 블롭으로 병합되는 것(성분 분리 자체가 실패).
- 결정: 자동 배치는 물론 제안형 UI도 보류. 대신 밑그림(언더레이) 위 가구 심볼
  자리에 카탈로그 아이템을 얹는 수동 배치 UX를 사용하고, 업로드 안내문에 명시.

## 계단 심볼 자동 인식 — 불채택 (2026-08-25 측정)

- 표본: 같은 Matterport 샘플 (계단 1곳 + 베란다 데크 포함).
- 방법: 계단 특징인 등간격 평행선 다발 검출 실험. 기존 벽 검출 경로에서는 계단
  디딤판 선이 대부분 최소 길이 임계에 걸러지고 스트링거 1개만 벽으로 오인식됨.
- 결과: 진짜 계단(도면 중앙) 정탐 **0건**(방향 화살표 겹침·간격 불규칙),
  베란다 데크 널빤지 오탐 **2건**(4선·8선 다발) — 정밀도·재현율 모두 실패.
- 결정: 자동 인식 불채택. 카탈로그에 '직진 계단'(0.9×3.0m)·'L자 계단'(1.8×1.8m)을
  두어 수동 배치하고, 워크스루에서 계단 응시+클릭을 층 전환 트리거로 사용.

## 문 심볼(호) 기하 인식 — 불채택, 갭 기반 채택 (2026-08-25)

- 관찰: 벽 선 검출이 끊긴 구간을 이어 벽을 만들 때, 그 자리의 래스터 밝은 갭
  (≈0.5~1.4m)이 곧 개구부 위치였음. 문짝 호(arc)는 갭 옆의 장식일 뿐.
- 결정: 호 기하 인식 대신 벽 선 위 밝은 갭 스캔(`findGapsAlongLine`)으로 개구부를
  생성 — 내벽=문(기본 열림), 외벽=창. 더 단순하고 도면 스타일에 강건.

## 스케일 자동 추정 — 채택하되 한계 명시 (2026-08-25 측정)

- 방법: 검출 벽 선 위 수직 어두운 런의 중앙값으로 벽 픽셀 두께를 재고, 실벽
  0.18m 가정으로 실세계 폭을 역산(원본 해상도 픽셀, 샘플점 5개, 6~40m 클램프).
- 결과: Matterport 실측 대비 BW F2 70.5㎡(실측 77, −8%) · FCL F2 85.9㎡(실측 77,
  +12%) — **데크 없는 층 기준 ±10% 수준**. 데크·베란다가 있는 층은 외부 공간이
  '공간'으로 잡혀 합계가 실내 실측보다 커짐(실내외 구분 미지원이 구조적 한계).
- 결정: 자동 추정을 초기값으로 쓰되, 에디터의 "스케일 맞추기"(기준선 1회) 보정을
  권장 경로로 안내. 벽 두께는 절대값(내벽 0.15/외벽 0.2m)이라 보정 후 재환산 불필요.

## 링크 공유 — URL 해시에 도면 담기 채택 (2026-11-25 측정)

- 배경: 공유 카드가 "준비 중"이었고 상단바 "공유" 버튼은 동작하지 않았습니다(45차 QA). 백엔드 없이 공유를 끝낼 방법이 필요했습니다.
- 방법: planIO v1 내보내기 객체(다른 층은 `floors` 로 덧붙임)를 deflate-raw 로 줄이고 base64url 로 적어 `#share=` 해시에 담았습니다. 해시는 서버로 가지 않습니다.
- 결과: 주소를 합친 링크 길이는 원룸 1,290자 · 25평 2,557자 · 34평 2,915자 · 샘플 1,681자입니다. 테스트가 25평 4,000자 이하를 고정합니다. 밑그림 이미지(data URL)는 담으면 길이 상한을 넘으므로 빼고, 뺀 사실을 공유 알림에 적습니다.
- 결정: 해시 방식을 채택했습니다. 받은 도면은 보기 전용으로 열고, "내 도면으로 복사" 전까지 받은 사람의 저장소를 쓰지 않습니다. 쓰기는 store 미들웨어(`readOnlyWhileShared`) 한곳에서 막습니다. 서버 저장 · 계정은 들이지 않습니다.

## 업로드 벽 인식 — 계단 직선화를 직교 보정으로 교체 (2026-11-25 측정)

- 증상: 직교 사각형 PNG 를 올려도 벽이 0.2m 기울고 9조각으로 쪼개졌습니다. 번들 샘플도 0.084m 기울었습니다(45차 QA B-01).
- 측정: 같은 입력을 단계별 함수에 차례로 넣어 좌표를 찍었습니다. 선 검출 · 병합 · 외곽 폐합까지는 모두 수평 · 수직이었습니다. 처음 기운 곳은 윤곽 계단 직선화였습니다. 짧은 변의 두 끝만 옮겨 이웃 변이 사선이 됐습니다. 외곽이 벽 중심선이 아니라 바깥 면(0.08~0.24m 밖)을 따라가 내벽 끝도 외벽과 엇갈렸습니다.
- 결정: 축에서 `ORTHO_SNAP_DEG`(10°) 안인 변만 수평 · 수직으로 펴고, 정점은 이웃 변 직선의 교점으로 다시 구합니다(`orthoSnap.ts`). 외곽은 벽 중심선으로 옮기고 내벽 끝은 교점에 잇습니다. 10°를 넘는 변은 사선으로 둡니다.
- 결과: QA PNG 는 벽 9 → 6, 최대 기울기 0.200 → 0m, 끝 틈 0.082 → 0m 입니다. 방 면적 46.43 · 22.57 · 22.32㎡ 는 벽 안쪽 면 기준 기대값과 0.1㎡ 안에서 맞습니다. 샘플은 벽 7 → 6, 기울기 0 입니다. 45° 외벽은 사선 벽 하나(45.0°)로 나옵니다.
- 한계: 내벽 자동 문은 갭 이음 허용(24px)과 문 최소 폭(0.5m)이 겹치지 않아, QA 입력 같은 축척에서는 원리상 잡히지 않습니다. 다음 라운드 후보입니다.

## 화면 폭 · 공용 컴포넌트 — 범위 결정 (2026-11-25)

- 최소 폭: `.app` 최소 폭을 1200 → 900px 로 내리고, 900px 미만은 "데스크톱 화면에 맞춰져 있어요" 안내를 띄웁니다. 1024px 로 두면 900~1023px 창에서 안내도 뜨지 않고 상단바 버튼이 잘렸습니다. 모바일 편집은 지원 범위 밖으로 둡니다.
- MODUL(gook-lab 공용 디자인 시스템): 이번에는 들이지 않았습니다. 이 앱은 자체 토큰 위에 서 있고 npm 을 씁니다. MODUL 패키지는 pnpm 으로만 설치됩니다. 들일 만한 후보는 Modal(`window.confirm` · `prompt` 대체)과 Toast(알림 셋 통일)입니다. 패키지 매니저 전환과 함께 다음 라운드에 다시 봅니다.

## 첫 화면 로딩 — 3D 청크 분리 · 인라인 시작 화면 · 정적 404 (2026-11-27 측정)

- 측정 방법: `scripts/measure-first-load.mjs` 를 씁니다. 프로덕션 빌드를 `vite preview` 로 띄우고 빈 캐시 Chromium(1440×900)으로 세 번 열어 중앙값을 냅니다. 조건은 제한 없음과 느린 망(CDP 4 Mbps 내려받기 · 2 Mbps 올리기 · 40 ms RTT) 둘입니다.
  - 쓸 수 있는 시각: 대시보드의 "새 도면 만들기" 버튼이 크기를 가진 첫 프레임입니다(페이지 안에서 매 프레임 확인).
  - 전송량: 그 시각부터 3초 안에 끝난 요청의 `encodedDataLength` 합입니다(gzip 기준, Google Fonts 포함).
- 병목: 앱 전체가 JS 한 덩어리(1,320KB, gzip 373KB)였습니다. 그중 대부분이 three.js · R3F · drei 입니다. 첫 화면인 대시보드는 3D 를 쓰지 않는데도 이 덩어리를 다 받고 실행해야 첫 그림이 나왔고, 그 전까지는 빈 흰 화면이었습니다. Google Fonts 스타일시트도 첫 그림을 막는 자리에 있었습니다.
- 결정:
  - 워크스루 · 조감도를 `React.lazy` 로 나눴습니다(`src/viewerChunks.ts`). 첫 화면 JS 는 441KB(gzip 140KB)가 됐습니다. 3D 는 공용 청크 830KB(gzip 219KB)와 화면별 21 · 31KB 입니다. 도면을 열면 쉬는 틈(`requestIdleCallback`)에 3D 를 미리 받아 탭을 바꿀 때 기다림을 숨깁니다.
  - 3D 청크를 받지 못하면 `ViewLoadBoundary` 가 [다시 시도] · [평면도로 돌아가기]를 띄웁니다. 새로고침 단추는 두지 않았습니다. 저장이 2초 디바운스라 마지막 편집을 잃을 수 있습니다. 다시 시도는 lazy 를 새로 만들어 실패를 기억하지 않게 했고, Chromium 에서 망을 되살린 뒤 조감도가 뜨는 것을 확인했습니다.
  - `index.html` 에 인라인 시작 화면을 넣었습니다(앱 이름 · 진행 막대). 15초가 지나면 느린 망 안내, 진입 스크립트 실패면 실패 안내, JS 꺼짐이면 안내를 띄웁니다.
  - 글꼴 스타일시트는 `media="print"` 로 받은 뒤 붙입니다. 원래 `display=swap` 이라 대체 글꼴로 먼저 그리던 동작은 같습니다.
  - 편집기(`Editor2D`) · 업로드는 나누지 않았습니다. 첫 화면 JS 의 나머지(React · 스토어 · 카탈로그 · 템플릿 · 썸네일)와 얽혀 있고, 나누면 도면을 열 때 기다림이 하나 더 생깁니다. 이득은 재지 않았고 다음 후보로 둡니다.
- 결과(세 번 중앙값):

| 조건 | 지표 | 전 | 후 |
| --- | --- | --- | --- |
| 제한 없음 | 첫 그림(FCP) | 228ms | 28ms |
| 제한 없음 | 쓸 수 있는 시각 | 218ms | 62ms |
| 느린 망 | 첫 그림(FCP) | 924ms | 148ms |

- 후의 첫 그림은 시작 화면입니다. 늘어난 요청 둘은 첫 방문 띠의 표지 그림(`cover-800.webp`, 27KB)과 브랜드 표식 `data:` 주소(망 요청 아님, 0B)입니다. 표지 그림을 넣고도 전송량은 절반 가까이 줄었습니다.
- 404: 배포 전 라이브(`roomcast-flame.vercel.app/<없는 주소>`)는 Vercel 기본 응답이었습니다(상태 404, `text/plain` "NOT_FOUND"). `vercel.json` 재작성이 없고 앱은 주소 경로를 쓰지 않으므로 SPA 재작성 대신 `public/404.html`(JS 없음, `noindex`, [처음 화면으로])을 뒀습니다. 배포 뒤에는 같은 404 상태로 이 화면이 나와야 합니다(배포 뒤 확인 필요).
